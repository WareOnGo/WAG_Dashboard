# Field review frontend

Reviewers and admins can create flags, verify responses, request changes, reopen fields and reassign work. The API enforces the reviewer capability and current warehouse View scope.

An active assignment lets employees submit responses to its open flagged fields even without warehouse Edit permission. They still need an active account and View access to the warehouse. Closing a flag ends response permission for that field; closing the review disables all response controls. Reopening restores those controls for the current assignee. Assignment never changes ordinary warehouse Edit grants. Reviewers may verify responses, including their own when assigned.

The `/field-reviews` route is available in desktop and mobile navigation. Employees see dashboard-style cards with Currently flagged / Previously flagged segments. Reviewers see To verify / Awaiting employee / Previously flagged / All, using the existing card and queue patterns.

`WarehouseDetailsModal` keeps its normal layout. Its fields have stable `fieldKey` attributes for highlights and reviewer flag selection. System metadata does not receive a checkbox. Only the complete Media section can be flagged; individual files retain their normal preview controls. The confirmation summary defaults assignment to the eligible uploader returned by the server. Options require View permission for this warehouse; if an existing assignee loses account or View access, the summary links to reassignment and disables adding flags. Creation setup/summary resets when the reviewer identity or role changes, and late requests from the previous session cannot restore it.

Normal warehouse View highlights each active flagged field in orange with a **Flagged for review** badge and its original reviewer note for every viewer, including unassigned employees. Notes render as plain text beside their respective fields. Proposals, employee response explanations and management controls retain their existing permissions. Availability and Last reviewed both highlight and show the note for their shared flag. Flagged RCC/lift fields remain visible even if the current warehouse type or lift setting would otherwise hide them. These markers also appear in the review dialog’s All details tab.

The dashboard requests `includeFieldReviews=true` on its existing warehouse-list call and stamps each row with the permission scope captured for that request. Cards and their View modal use the bundled `fieldReviewSummary` immediately, including explicit empty summaries, without another review request. Identity/permission changes invalidate the payload and late responses; server-side 401/403 responses clear cached cards and the open preview. Review mutations refresh the dashboard list. An already open preview can refresh independently, showing an animated loading status while retaining known fields; unbundled callers use the summaries endpoint with the same loader and retry behavior. Changes in another browser require a list refresh; this is a snapshot, not a live subscription.

`useFieldReviewHighlights` uses bundled flags on opening a live warehouse, falls back to a lookup for unbundled rows, and refreshes after review actions. Closed fields lose their marker; reopened fields regain it. New refresh results and errors supersede the source bundle across closing/reopening, including when the independent card-list refresh fails. Closing during a pending refresh cancels its request but retains the invalidation so reopening resumes it. Identity, View scope, warehouse and replacement-bundle changes discard old results. A failed refresh offers Retry, retaining known flags only for the same authorized view; authorization failures clear them. Staged rows do not request live field markers.

`FieldReviewDialog` owns response drafts and each tab's scroll. Flagged fields contains the response controls. All details renders the existing `WarehouseDetailsModal` with flag creation disabled. Employee proposals never replace live values shown in that view.

The queue URL is the source of truth for the open review. Identity/role changes reset queue state and cancel old requests. A late refresh cannot replace a newer successful mutation on screen. Reviewer replacement prompts use the server's semantic comparison, so formatting-only differences do not ask for an overwrite reason.

Reviewers can combine **Assigned to** and a single admin selector with the existing stage chips. Its label explains the match: **Flagged by** for the creator of active fields in the current stage, **Closed by** for fields verified or cancelled in completed reviews, and **Admin / reviewer** for any historical review action in **All**. A flagger is not treated as the approver when another admin closes the review. The dropdown searches names and emails from accessible history, including former reviewers. Suggestions load independently of queue pages, search and stage; scope changes and refresh reload them. The selection persists across manual and AI stages and resets pagination. **Clear All Filters**, including the filter panel's Reset, clears admin, assignee, search and warehouse filters while preserving the stage. Active-filter counts include both people filters. Employee queues do not show these controls.

AI flags use the same selected admin. **Approved by** and **Dismissed by** match the admin who confirmed that outcome. **Reviewed by** in pending reviews matches saved human review actions; automated evaluations and batch creation have no reviewing admin. AI suggestions are scoped to the selected batch and filtered totals, metrics and pagination come from the server. Clear All Filters also returns AI reviews to All batches while preserving the selected status. Identity and permission changes discard suggestions and abort pending requests.

Creation, the queue, the detail dialog and dashboard markers share `fieldReviewAccessKey`. It changes with identity, reviewer access and warehouse View/Edit scope, so each surface invalidates stale results consistently.

`ReviewField` handles direct correction/no-change responses, ordinary reviewer verification, returns, the three conflict choices, protected values, edit history and reopening. Submitted responses stay read-only until returned by a reviewer. A stale employee draft preserves its input and requires explicitly checking the refreshed baseline. A stale reviewer comparison clears the choice, reason and confirmation on refresh or reopening, even if only the live value's revision changed.

Review correction inputs and `WarehouseForm` share `WarehouseFormControls`, form options and control styles. This includes searchable State/City choices, dropdowns that preserve legacy values, calendars with DD/MM/YYYY entry, Yes/No switches, ordered **Add Space Value** inputs and Handover. Measurements, phone numbers, ventilation and washrooms continue to use `StructuredFields`. Labels follow the current edit form, including Compound Gate Width, Security Features, Floor Strength, Lighting and Parking Space Availability.

City options follow the employee's proposed State where present; State and Zone remain separate review items. This does not change the live warehouse or apply unflagged fields. Handover never supplies an unchosen lead-time unit. Proposals and reviewer choices apply the selected timing type and keep the latest saved values for the other type unchanged. Required-field validation follows the warehouse form's current policy. Allowed date changes remain proposed corrections until reviewer verification. String-backed Yes/No switches keep their stored string type.

Availability and Last reviewed form one `availabilityReview` item. The existing View retains its two normal fields, with one checkbox and a note explaining that they are reviewed together. The employee edits both in one card; changing Availability clears the previous review date and asks for the date this answer was checked. Baseline, Proposed, Current, confirmation and history show both values. Each reviewer choice applies the pair together, and a newer edit to either clears an outdated reviewer choice/confirmation. No change needed retains its required explanation. All details continues to show live values while the proposed pair is pending.

`CardView` batches marker lookups for the visible dashboard cards. Active markers include Awaiting reviewer. Successful review writes refresh local queues/markers. A failed marker refresh preserves known flags only within the same authorization scope and offers Retry. Role changes immediately hide old markers and links, refetch their current permissions and ignore late responses from the old role. Employees who are not assigned see the marker without a link to protected review details.

The production backend migration is required before this UI is enabled. Deployment instructions, API contracts, security rules and V1 limits are in `Backend_Repository/docs/field-review.md`. The resolved Availability/review-date defect and its regression coverage are documented in [the adversarial review](../../Backend_Repository/docs/field-review-adversarial-review.md).

## Media review (19 November 2026)

The single **Media section** checkbox works even for an empty gallery. It flags images, videos and documents together with one comment. Individual files have no flagging controls and retain the existing View previews. The section uses the same orange marker and note as data fields.

1. **Reviewer:** Open the existing View, select Media section, describe what needs checking or adding, then confirm the summary and uploader-default assignment.
2. **Employee:** Open Flagged fields and edit the proposed gallery with the shared `FileUpload` control. Add missing files, remove outdated files or upload replacements; add a verification note and submit. **No change needed** retains the required explanation. Scoped uploads work for assigned employees with View access without granting normal Edit access. Pending uploads disable submission, and closing the editor aborts them and ignores late results. The upload control sends the server-signed headers so review uploads cannot overwrite existing objects. The backend checks new uploads before submission and approval; missing files or storage errors leave the draft/flag available for recovery. All details retains the actual existing View and live gallery.
3. **Reviewer:** Inspect media previews/links and verify the response. If any gallery change happened in transit—including deletion, addition or reordering—compare Baseline / Proposed / Current and expand Current's available edit history. Earlier media/photos audits are labeled as recorded fields; their stored values are preserved even when a complete gallery snapshot is unavailable. The choice applies to the whole gallery; replacing Current requires a reason and confirmation. A later edit requires a refreshed comparison.

A flag requesting missing images needs no existing image to attach to. Deleting a photo through normal editing leaves the section flag open and advances its revision; it makes an unsubmitted employee draft stale or triggers comparison for a submitted response. A fully emptied gallery can still receive a proposal or no-change response. Normal View/Edit stays available. Review decisions remove references, not storage objects; historical previews depend on the stored files remaining available.

The updated backend migration must be applied before enabling these controls. Media changes are local and not deployed. See the backend implementation document's **Media review** section for the full workflow, concurrent-edit rules, storage retention and limits. The browser flow in `e2e/field-review-media.e2e.mjs` covers section-only selection, a staged upload/replacement, ordinary deletion while verification is pending, edit history, and explicit whole-gallery approval at 1280 px and 390 px. Signing/storage are local fixtures; review API calls, authentication and PostgreSQL transactions are real.

## Tests

```sh
npm test -- src/components/fieldReview/__tests__
npm run build
```

The component suite covers uploader selection and Back navigation, direct employee responses, required no-change explanation, draft/scroll preservation using the real All details component, stale-draft recovery, late refreshes, identity/role changes, unconfirmed handover timing, semantic value comparisons, three-value reviewer confirmation and marker refresh failures. Dashboard tests cover role grants/revocations, late old-role summaries and failed refreshes after an authorization change. Field-highlight tests cover unassigned viewers, linked/conditional fields, closing/reopening, late results across warehouses and identities, access revocation and retry. Input tests cover shared options, legacy values, ordered areas, measurement validation and stored boolean/string types. Normal form tests check that sharing the controls preserves existing create/edit payloads.

The browser suite uses real production components, API client, JWT middleware, review routes/service and isolated PostgreSQL. Only sign-in and the surrounding dashboard list-loading shell are fixtures. The workflow runs for both admin and reviewer accounts. The reviewer has View all and Edit own permissions, without Admin or Edit all. The employee test account has View own permission, no Edit grants, and is the warehouse's uploader. The lifecycle verifies that response controls disappear after closure and return only for reopened fields. No review API responses are mocked in this workflow.

Start a disposable PostgreSQL instance on localhost with the test URL below, then:

```sh
TEST_DATABASE_URL=postgresql://warehouse_test:warehouse_test@127.0.0.1:55445/warehouse_qa E2E_BROWSER_PATH=/usr/bin/google-chrome npm run test:e2e -- e2e/field-review.e2e.mjs --output=/tmp/field-review-browser-artifacts --reporter=list
```

`E2E_BROWSER_PATH` is optional when Playwright Chromium is installed. Each run creates and drops a random schema. The database URL guard refuses non-test databases. The test checks the full create/respond/conflict/no-change/history/reopen flow at 1280px and 390px, verifies live values in the database, asserts no horizontal overflow and saves screenshots for review. A second flow exercises the shared State/City, Handover, area and measurement inputs, preserves drafts across All details, and checks that submissions remain staged. A third flags the availability pair, submits a date correction, detects an intervening Availability edit and rejects a second edit made while the reviewer's confirmation is open. Run `e2e/form.e2e.mjs` alongside this suite when changing shared controls to verify normal creation, staged review and editing at 320px, 390px and 1280px. Test entry points under `e2e/` are not included in the production build.
